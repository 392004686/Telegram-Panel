# 命令控制台：A/B 账号与群组客户任务设计记录

状态：方案已记录，模块实现尚未开始

记录日期：2026-09-23

本文记录命令控制台后续支持“A 组维护群资产、B 组执行客户任务”的设计决策。本文是模块侧的编排和观察方案，不替代任务中心的持久化执行器设计，也不直接修改现有任务中心代码。

## 1. 目标和边界

命令控制台负责：

- 通过白名单命令调用宿主已有账号、代理、群组和客户服务；
- 在执行前检查账号、代理、群权限、邀请链接和群成员；
- 以中文事件流显示每一步为什么执行、跳过、等待或暂停；
- 复用宿主已有的邀请确认逻辑，不把 Telegram 接受 RPC 请求误判为客户已入群；
- 为以后把同一套结构化事件搬到任务中心执行日志预留数据格式。

命令控制台不负责：

- 自行创建 Telegram Client；
- 绕过宿主代理和账号生命周期；
- 通过更换 API、代理或 Session 规避 Telegram 限制；
- 直接操作任务中心数据库；
- 在未明确授权的情况下批量触达客户。

## 2. 账号分组

### 2.1 A 组：群资产维护账号

示例：`A1`、`A2`、`A3`、`A4`。

A 组负责创建和长期维护私人群组、保留创建者身份、生成邀请链接和刷新群状态。A 组不参与批量客户邀请，尽量保持固定代理和低频操作。

### 2.2 B 组：任务执行账号

示例：`B1`～`B10`。

B 组负责按任务领取一个可用群组，加入群组，处理符合条件的客户，执行批准的消息规则，完成后退出并释放任务资源。一个 B 账号同一时间只能执行一个批次。

## 3. 群组可用条件

B 账号选择群组时必须同时满足：

- 群组状态正常；
- A 组创建者仍在群内；
- 邀请链接有效；
- 群权限允许 B 账号加入和邀请；
- 群组没有被其他任务占用；
- 当前 B 账号不在群内；
- 群内除 A/B 组账号外没有任何客户或外部成员；
- 群组未标记为异常、封禁、待清理或冷却中；
- 可用客户数量满足本批次的最低邀请数量。

群成员检查规则：

| 成员类型 | 处理 |
|---|---|
| A 组账号 | 允许 |
| B 组账号 | 允许，但要确认没有占用其他任务 |
| 已导入客户 | 发现即跳过该群 |
| 未识别外部成员 | 跳过并要求人工核对 |

只要群内存在客户或未识别外部成员，就不能把群当作干净群复用。客户在本系统中被标记为已退出，不代表 Telegram 群成员快照中已经不存在该客户。

## 4. 客户处理模型

当前模块先使用已有的客户执行状态。后续可补充下列状态：

```text
待执行 → 已领取 → 邀请中 → 待确认 → 已进群
                         ├→ 客户级失败
                         ├→ 等待重试
                         └→ 永久排除
```

“客户授权”是业务状态，不是 Telegram 技术权限。若当前客户导入流程已保证客户属于执行范围，可以先用“待执行”表示可处理；但应保留拒绝、已沟通和永久排除状态，避免重新导入后重复触达。

## 5. 邀请确认和随机间隔

每个客户的邀请必须经过以下阶段：

1. 解析客户并检查是否已在群内；
2. 提交邀请请求；
3. 读取 Telegram 返回的缺失邀请信息；
4. 检查 updates 证据；
5. 刷新成员快照并进行短重试；
6. 最终确认成员出现后才记为成功；
7. 未确认时标记“请求已接受但成员未确认”，不能直接记为成功。

邀请间隔采用区间配置：

```text
minDelaySeconds = 30
maxDelaySeconds = 60
```

每次动作后重新生成等待时间。这个设置仅用于业务节奏控制，不保证绕过 Telegram 风控；若 Telegram 返回 `FLOOD_WAIT_X`，必须以 Telegram 指定的等待时间为准。

## 6. 失败分类和暂停规则

### 6.1 客户级失败

客户注销、用户名无效、隐私限制、拒绝邀请、需要 Premium、客户已在群内等，只记录客户结果，不累计 B 账号连续失败。

### 6.2 账号级硬失败

`FROZEN_METHOD_INVALID`、Session 失效、账号注销、账号封禁、邀请权限被撤销、明确的账号级 `PEER_FLOOD` 等，立即暂停该 B 账号，保留恢复点，不再领取新批次。

### 6.3 系统或网络失败

网络超时、代理瞬断、Telegram 临时错误、数据库写入失败等，进入有限重试或延迟状态，不直接计为邀请失败。

### 6.4 邀请请求已接受但成员未确认

这是需要单独统计的“疑似账号级失败”。只有在不同的有效客户上连续出现三次，并排除客户隐私、注销和网络原因后，才暂停当前 B 账号。该规则用于避免把三个无效客户误判为账号故障。

## 7. 单线程和锁设计

测试阶段先使用单线程执行，但从第一版数据结构开始保留三种逻辑锁：

```text
account:{accountId}
group:{telegramGroupId}
customer:{customerId}
```

锁的语义：

- 账号锁：一个 B 账号只能执行一个批次；
- 群组锁：一个群只能被一个任务占用；
- 客户锁：一个客户不能同时被两个任务领取。

状态建议：

```text
账号：Idle → Reserved → Running → Cooling/Paused → Idle
群组：Available → Inspecting → Occupied → Cleaning → Available
客户：Pending → Reserved → Inviting → Confirming → Completed/Failed
```

以后增加多线程时，再将逻辑锁实现为数据库租约、过期时间和幂等令牌。单线程版本也必须在日志中输出锁的获得和释放，方便验证恢复逻辑。

## 8. 建议的模块命令

### 8.1 检查和预览

```text
engagement.pool.refresh creatorGroup=A
engagement.group.inspect group=G1
engagement.account.health account=B1
engagement.customer.eligible category=1
engagement.batch.preview account=B1 inviteCount=3 minSuccess=1
```

### 8.2 执行和恢复

```text
engagement.batch.run account=B1 inviteCount=3 minSuccess=1 delayMin=30 delayMax=60
engagement.batch.pause account=B1
engagement.batch.resume run=批次ID
engagement.group.cleanup group=G1
```

### 8.3 查询和审计

```text
engagement.run.get run=批次ID
engagement.run.list status=paused
engagement.failure.list account=B1
engagement.group.available
```

命令必须使用固定白名单和强类型参数；缺少账号、群组、客户或最低成功数时直接拒绝生成命令。

## 9. 中文运行上下文

模块输出应该突出选择依据和失败归因，而不是只输出原始 JSON。建议维护以下事件映射：

| 事件 | 中文显示 |
|---|---|
| `pool.refreshed` | 资源池刷新 |
| `account.health.checked` | 账号健康检查 |
| `proxy.checked` | 代理状态确认 |
| `group.candidate.filtered` | 群组候选筛选 |
| `group.members.checked` | 群组成员检查 |
| `lock.acquired` | 资源锁已获得 |
| `customer.reserved` | 客户已领取 |
| `invite.submitted` | 邀请请求提交 |
| `invite.confirmed` | 邀请结果确认 |
| `invite.unconfirmed` | 邀请未确认 |
| `failure.classified` | 失败原因归类 |
| `account.circuit_opened` | 账号触发熔断 |
| `group.cleaned` | 群组清理确认 |
| `lock.released` | 资源锁释放 |
| `run.paused` | 批次暂停 |
| `run.completed` | 批次完成 |

运行结果需要展示：执行账号、代理出口、API/Session 状态、群组选择原因、成员检查结果、客户状态、确认等待、失败归类、暂停原因以及锁释放状态。

## 10. 模块输出与任务中心审计

模块使用流程卡片或树形事件流，适合实时观察：

```text
✔ 账号健康　B1 正常
· 网络出口　代理 #12
✔ 群组检查　仅存在 A/B 组账号
✔ 群组锁　已获得
▶ K21　提交邀请
✔ K21　成员快照确认入群
⚠ K22　客户隐私限制，不计入账号失败
· 下一次执行　等待 47 秒
✔ 批次完成　成功 1，客户级失败 1
✔ 锁释放　账号、群组、客户
```

任务中心继续保留表格、分页、筛选和 CSV 导出，作为正式审计入口。后续不要把格式化文本直接复制到任务日志，而是统一保存结构化事件：

```text
EventType, RunId, AccountId, GroupId, CustomerId,
Result, ErrorCode, ChineseMessage, OccurredAtUtc, ContextJson
```

这样同一份事件既能在模块中渲染成易读流程，也能在任务中心中用于审计、筛选和统计。
