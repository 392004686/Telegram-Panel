# 命令控制台：A/B 账号与群组客户任务设计记录

状态：方案已记录，命令控制台模块首轮实现已完成；任务中心持久化和多线程仍未接入

记录日期：2026-09-23

本文记录命令控制台后续支持“A 组维护群资产、B 组执行客户任务”的设计决策。本文是模块侧的编排和观察方案，不替代任务中心的持久化执行器设计，也不直接修改现有任务中心代码。

## 1. 目标和边界

命令控制台负责：

- 通过白名单命令调用宿主已有账号、代理、群组和客户服务；
- 在执行前检查账号、代理、群权限、邀请链接和群成员；
- 以中文事件流显示每一步为什么执行、跳过、等待或暂停；
- 复用宿主已有的邀请确认逻辑，不把 Telegram 接受 RPC 请求误判为客户已入群；
- 为以后把同一套结构化事件搬到任务中心执行日志预留数据格式。

命令控制台不负责：

- 自行创建 Telegram Client；
- 绕过宿主代理和账号生命周期；
- 通过更换 API、代理或 Session 规避 Telegram 限制；
- 直接操作任务中心数据库；
- 在未明确授权的情况下批量触达客户。

## 2. 账号分组

本文中的 `A1`、`B1`、`G1`、`K1` 仅是帮助理解流程的临时别名，不是正式字段，也不应直接写入命令、数据库或审计记录。正式实现必须使用宿主已有的实际标识和分类字段。

| 概念 | 正式字段/来源 |
|---|---|
| 账号 | `accountId` |
| 账号分组 | `accountCategoryId` 或宿主账号分类 ID |
| Telegram 账号 | `telegramUserId` |
| 群组记录 | `groupId` |
| Telegram 群组 | `telegramGroupId` |
| 客户记录 | `customerId` |
| Telegram 客户 | `telegramUserId` |
| 执行批次 | `runId` / `batchTaskId` |

命令参数也应使用正式字段，例如：

```text
engagement.batch.preview accountCategoryId=12 telegramGroupId=-1001234567890 customerCategoryId=8
engagement.batch.run accountId=27 telegramGroupId=-1001234567890 customerCategoryId=8
```

实际字段名称以宿主 API 和数据模型为准；命令映射层负责转换，不重新创造 A/B/G/K 编号。

### 2.1 A 组：群资产维护账号

示例：`A1`、`A2`、`A3`、`A4`。

A 组负责创建和长期维护私人群组、保留创建者身份、生成邀请链接和刷新群状态。A 组不参与批量客户邀请，尽量保持固定代理和低频操作。

### 2.2 B 组：任务执行账号

示例：`B1`～`B10`。

B 组负责按任务领取一个可用群组，加入群组，处理符合条件的客户，执行批准的消息规则，完成后退出并释放任务资源。一个 B 账号同一时间只能执行一个批次。

## 3. 群组可用条件

B 账号选择群组时必须同时满足：

- 群组状态正常；
- A 组创建者仍在群内；
- 邀请链接有效；
- 群权限允许 B 账号加入和邀请；
- 群组没有被其他任务占用；
- 当前 B 账号不在群内；
- 群内除 A/B 组账号外没有任何客户或外部成员；
- 群组未标记为异常、封禁、待清理或冷却中；
- 可用客户数量满足本批次的最低邀请数量。

群成员检查规则：

| 成员类型 | 处理 |
|---|---|
| A 组账号 | 允许 |
| B 组账号 | 允许，但要确认没有占用其他任务 |
| 已导入客户 | 发现即跳过该群 |
| 未识别外部成员 | 跳过并要求人工核对 |

只要群内存在客户或未识别外部成员，就不能把群当作干净群复用。客户在本系统中被标记为已退出，不代表 Telegram 群成员快照中已经不存在该客户。

### 3.1 完整场景示例

本节的 `A1`、`B1`、`G1`、`K1` 等名称全部是叙事别名。实现时必须将它们替换为 `accountId`、`accountCategoryId`、`groupId`、`telegramGroupId`、`customerId` 和 `telegramUserId` 等真实值；别名不能成为数据库主键或接口参数。

假设当前资源如下：

```text
A 组：A1、A2、A3、A4
每个 A 账号维护 10 个群：G1～G10
B 组：B1～B10
客户池：K1～K100
```

第一阶段由 A 组刷新群状态：

```text
A1 → G1～G10
A2 → G11～G20
A3 → G21～G30
A4 → G31～G40
```

刷新后，每个群组需要记录：

- Telegram 群组 ID；
- 创建者账号；
- A 组创建者是否仍在群内；
- 当前成员数量；
- A/B 组成员数量；
- 客户成员数量；
- 未识别外部成员数量；
- 邀请链接和权限；
- 最近一次成员同步时间；
- 当前任务占用和冷却状态。

例如 B1 检查 G1～G10 时：

```text
G1：只有 A1、B2，允许候选
G2：存在客户 K17，跳过
G3：A1 已退出，跳过
G4：邀请链接失效，跳过
G5：B1 已在群内，跳过
G6：存在未识别成员，跳过并标记人工核对
G7：正在被 B2 任务占用，跳过
G8：权限不足，跳过
G9：冷却中，跳过
G10：只有 A1，允许候选
```

因此 B1 只能在 G1 和 G10 中择一执行。群组不是“没有 B1 就可用”，而是必须是只包含允许的 A/B 组成员的干净群。

### 3.2 一次批次示例

假设配置为：

```text
执行账号：B1
目标群组：G1
每批计划邀请：3 人
最低成功人数：1 人
间隔范围：30～60 秒
客户顺序：K1、K2、K3、K4……
```

执行过程可能是：

```text
K1：接口提交成功，成员快照确认入群，成功 1 人
K2：客户隐私限制，客户级失败，不计 B1 失败次数
K3：Telegram 接受请求，但短重试后成员快照未确认，疑似失败 1/3
```

因为 K1 已成功，已达到最低成功人数。后续可以继续处理 K3，但如果再出现两个“请求接受但成员未确认”的有效客户，则暂停 B1 当前进度。

如果最终结果为：

```text
成功：K1
客户级失败：K2
疑似账号级失败：K3、K4、K5
```

则 B1 进入暂停状态。退出前应检查群成员：

- 如果群内除了管理员没有客户，B1 退出并释放 G1；
- 如果 K1 已确认入群，必须按照任务配置决定是否执行消息规则；
- 如果消息规则不满足或发送失败，不得把 K1 标记为“已沟通”；
- A1 继续留在群内，G1 标记为待清理或可复用，取决于客户是否仍在群内。

## 4. 客户处理模型

当前模块先使用已有的客户执行状态。后续可补充下列状态：

```text
待执行 → 已领取 → 邀请中 → 待确认 → 已进群
                         ├→ 客户级失败
                         ├→ 等待重试
                         └→ 永久排除
```

“客户授权”是业务状态，不是 Telegram 技术权限。若当前客户导入流程已保证客户属于执行范围，可以先用“待执行”表示可处理；但应保留拒绝、已沟通和永久排除状态，避免重新导入后重复触达。

## 5. 邀请确认和随机间隔

每个客户的邀请必须经过以下阶段：

1. 解析客户并检查是否已在群内；
2. 提交邀请请求；
3. 读取 Telegram 返回的缺失邀请信息；
4. 检查 updates 证据；
5. 刷新成员快照并进行短重试；
6. 最终确认成员出现后才记为成功；
7. 未确认时标记“请求已接受但成员未确认”，不能直接记为成功。

邀请间隔采用区间配置：

```text
minDelaySeconds = 30
maxDelaySeconds = 60
```

每次动作后重新生成等待时间。这个设置仅用于业务节奏控制，不保证绕过 Telegram 风控；若 Telegram 返回 `FLOOD_WAIT_X`，必须以 Telegram 指定的等待时间为准。

## 6. 失败分类和暂停规则

### 6.1 客户级失败

客户注销、用户名无效、隐私限制、拒绝邀请、需要 Premium、客户已在群内等，只记录客户结果，不累计 B 账号连续失败。

### 6.2 账号级硬失败

`FROZEN_METHOD_INVALID`、Session 失效、账号注销、账号封禁、邀请权限被撤销、明确的账号级 `PEER_FLOOD` 等，立即暂停该 B 账号，保留恢复点，不再领取新批次。

### 6.3 系统或网络失败

网络超时、代理瞬断、Telegram 临时错误、数据库写入失败等，进入有限重试或延迟状态，不直接计为邀请失败。

### 6.4 邀请请求已接受但成员未确认

这是需要单独统计的“疑似账号级失败”。只有在不同的有效客户上连续出现三次，并排除客户隐私、注销和网络原因后，才暂停当前 B 账号。该规则用于避免把三个无效客户误判为账号故障。

## 7. 单线程和锁设计

测试阶段先使用单线程执行，但从第一版数据结构开始保留三种逻辑锁：

```text
account:{accountId}
group:{telegramGroupId}
customer:{customerId}
```

锁的语义：

- 账号锁：一个 B 账号只能执行一个批次；
- 群组锁：一个群只能被一个任务占用；
- 客户锁：一个客户不能同时被两个任务领取。

状态建议：

```text
账号：Idle → Reserved → Running → Cooling/Paused → Idle
群组：Available → Inspecting → Occupied → Cleaning → Available
客户：Pending → Reserved → Inviting → Confirming → Completed/Failed
```

以后增加多线程时，再将逻辑锁实现为数据库租约、过期时间和幂等令牌。单线程版本也必须在日志中输出锁的获得和释放，方便验证恢复逻辑。


```text
engagement.run.get run=批次ID
```

命令必须使用固定白名单和强类型参数；缺少账号、群组、客户或最低成功数时直接拒绝生成命令。


任务中心继续保留表格、分页、筛选和 CSV 导出，作为正式审计入口。后续不要把格式化文本直接复制到任务日志，而是统一保存结构化事件：

```text
EventType, RunId, AccountId, GroupId, CustomerId,
Result, ErrorCode, ChineseMessage, OccurredAtUtc, ContextJson
```

这样同一份事件既能在模块中渲染成易读流程，也能在任务中心中用于审计、筛选和统计。

### 11.1 当前对话中已确认的设计决策

这些决策属于本方案的固定约束，后续实现不能无提示地改回旧行为：

| 决策 | 固定要求 |
|---|---|
| 群组成员 | 发现客户或未知外部成员时跳过，不能只检查 B 账号是否已在群内 |
| 邀请间隔 | 使用 30～60 秒随机区间；Telegram 的 `FLOOD_WAIT_X` 优先 |
| 失败统计 | 客户级、账号级、系统级分开；客户隐私失败不计账号失败 |
| 邀请成功 | RPC 接受不等于成功，必须经过成员快照确认 |
| 疑似账号失败 | 不同有效客户连续三次未确认，才暂停 B 账号 |
| 并发 | 当前先单线程；账号、群组、客户锁模型必须预留 |
| 执行入口 | 先通过命令控制台模块调用宿主能力，不直接改任务中心执行器 |
| 展示方式 | 模块显示流程卡片，任务中心保留表格和审计日志 |
| 后续迁移 | 迁移结构化事件，不复制格式化文本 |
